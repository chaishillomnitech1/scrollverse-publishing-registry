### How a document becomes a composition

The registration **is** the vault record. The document's text does not live in Vydia. It lives in two places, and only two:

1. **The manuscript as the composition's lyrics.** A book is a spoken-word composition: the words are the lyrics. 2. **The companion spoken-word audio, when it is recorded.** When a document is recorded as spoken word, the audio goes through Add Content > Audio as its own single, and the composition registration and the recording are linked by title. The audio is the only form in which the document's full text ever enters Vydia — and only as sound, never as readable text.

Vydia's own note on audio, from the same help page:

> "Please note, if you do have an audio file for a recording of your composition go back to the 'Add Content' section, select 'Audio' and **only assert the rights for which you own and/or control**."

## Chapter 4 — The Double Stamp

### Two stamps, one work

Every vaulted document carries two stamps:

1. **The GitHub stamp** — commit SHA + timestamp. The document already lives in a repo with a verifiable commit. The commit is the dated, attributed record that the document existed in that form, at that time, by that author.
2. **The Vydia stamp** — composition registration + ISWC + registration date. The registration is the dated, attributed record that the work exists as a composition, under his publishing, held by a music distributor.

That is the protection and the validation: two independent, dated, attributed records of the same work, held by two different systems, under two different authorities. If one record is ever questioned, the other stands. If both are questioned, they corroborate each other — same work, same author, same publisher, two timestamps from two systems that do not talk to each other.

### What each stamp is, exactly

**The GitHub stamp** for a document is three values:
- The **blob SHA** — the hash of the file's content at the commit. If the content changes by one character, the blob changes. The blob is the fingerprint of the text.
- The **HEAD commit SHA** — the commit that holds the blob. The commit is the dated event.
- The **commit timestamp** — when the commit was made, and by whom (author + committer, on record as Chais Hill).

For documents that live in the workspace but not yet on GitHub — the 8 book manuscripts are the main case; the audit confirmed the 8 Infinite Material books are not on GitHub — the GitHub stamp is **pending**. The step is defined: commit the manuscript to a repo, record the blob SHA + commit SHA + timestamp, and the stamp is complete. A document with only the Vydia stamp is half-stamped; the registry says so plainly until the GitHub stamp lands.

**The Vydia stamp** for a document is three values:
- The **composition registration** — the title as registered in Vydia's Composition Content folder, with the date it was registered.
- The **ISWC** — blank until ASCAP issues it, then filled in.
- The **registration date** — the date Vydia accepted the registration.

**The local anchor** behind both stamps is the file's SHA-256, held in the vault registry with the source path. Three hashes, two systems, one work: blob SHA (GitHub), SHA-256 (local file), ISWC (the composition's own identifier). None of them is the others' substitute.

### What the double stamp proves — and what it does not

It proves: the work existed in that form, at that time, by that author, under that publisher, in two independent systems. It is evidence of authorship, of date, and of publishing ownership.

It does not prove: that the work will earn money (Vydia guarantees no royalties); that the work is legally registered for copyright (copyright registration is a separate filing, Form PA for the composition and Form SR for the recording, not done for these works on this record); or that any third party accepts the registration as conclusive. It is a record, not a ruling. This book does not claim otherwise.

### The pilot and the double stamp

The pilot — the first registration — was chosen because it is the one document that can carry **both stamps on day one**. The ScrollVerse Manifesto & Builders Book already lives in a repo with a verifiable commit, and its text is clean of every gate in this book. Its Vydia stamp is the only thing missing. When it registers, the double stamp is complete in a single act, and the system is proven end to end. Chapter 9 tells that story in full.

## Chapter 6 — The Licensing Interplay: Two Licenses, Two Objects

### The compositions are licensed works

Each registration is a licensing record under his publishing (ASCAP, Chais Kenyatta Hill, IPI 1247873912, XLVIIIBlock LLC, 100%) and the Vydia agreement. That is what a composition registration is: a work, an author, a publisher, a set of rights asserted, and a set of policies — filed with a distributor who delivers it to the PROs and the CMOs. The registration licenses the composition under that framework. The Vydia agreement is the license: it grants Vydia the exclusive DSP Rights and Vydia Rights over the Client Content, worldwide, for the Term (through 20 June 2027), and it pays Royalties as Gross Receipts less the Vydia Service Fee less expenses.

### The code is MIT-licensed

The GitHub repos are MIT-licensed — most of them open source, MIT-licensed, live to the public. The MIT license is a permissive open-source license: anyone may use, copy, modify, and distribute the code, with the copyright notice attached. That is the code's own license, and it stands on its own.

### The two licenses do not conflate

**Registering a document as a Vydia composition does NOT relicense the code.** The composition license covers the composition — the registered work. The code's own license stands. Two licenses, two objects:

- **The composition license** (Vydia agreement + ASCAP publishing) covers the registered work: the document as a spoken-word composition, the song as a musical composition, the arrangement as a derivative composition. It governs the composition's performance, mechanical, sync, and print income, and Vydia's rights to claim and collect on it.
- **The MIT license** covers the code: the programs, the build systems, the runnable files. It governs who may use, copy, and modify the code. It is unaffected by any composition registration.

A registration must not claim rights over code it does not cover. That is why the composition's title and metadata must identify the **document** (the spec, the doc, the manuscript), not the codebase. The registration says: this document, as a spoken-word work, is a composition under my publishing. It does not say: this codebase is now mine under a different license. The codebase was already his, already MIT-licensed, already public. The composition adds a second record of the document — it does not rewrite the first record of the code.

### What code takes as a composition — the honest design

A composition is a musical work. A code file is not a musical work. Chais's direction (10:19 EST) is that code and build programs **are** in the vault. The design, worked out honestly, is that code takes **three forms** as a composition — and one form it does not take:

1. **The code's written documentation or spec, as the composition.** The README, the architecture record, the API documentation, the deployment summary — the written record of what the code does and how it works — registers as a spoken-word composition. The document text is the lyrics. This is the primary form, and it is the form the GitHub survey was built to find: documentation is what transfers.
2. **A spoken reading of the code, as audio.** The code read aloud — a spoken-word single through Add Content > Audio — is the program performed. Vydia accepts audio uploads; a spoken reading is audio. The code text is carried as sound, never as a file. This form is real but secondary: it is slow to produce, and it is only worth doing for the programs that matter most.
3. **The code text in a metadata or lyrics field — not available.** No lyrics field was found in the account, Composition Only takes metadata rather than file uploads, and a code file cannot be pasted into a metadata field at any real length (field limits are unverified). The code text does **not** go in Vydia metadata. This book says so plainly, so no one mistakes the design: the code stays on GitHub; the registration carries the title, composer, publisher, splits, ISWC, and timestamp — and the documentation is the composition.

**What stays on GitHub, always:** the code files themselves, the runnable programs, the build systems, the dependencies, the configuration. The Vydia registration never holds them, never replaces them, and never relicenses them.

### Why the distinction protects him

The Vydia agreement's §6(a) grant is exclusive and broad — Vydia may authorize DSPs, make claims, block or monetize uses, create fingerprints, collect royalties, and "sell copies of" the Client Content. If a registration were framed as covering a codebase, that grant would reach toward the code. Framed correctly — the composition is the document, the code stays MIT-licensed on GitHub — the grant reaches only the registered work. The licensing interplay is not a technicality. It is the fence that keeps the vault from swallowing the workshop.
