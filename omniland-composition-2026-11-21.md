## 1. Console-less delivery — how the leaders actually do it, and what is true

There are exactly three working models for "play on any device with no console." They differ in **where the game renders**, and that one fact decides the cost of everything.

### Model A — Cloud streaming (the game renders on someone else's GPU)

The game runs on a server GPU; each frame is encoded as video (H.264/HEVC/AV1) and streamed to the device, which sends inputs back — browser services ride on WebRTC. This is GeForce NOW and Xbox Cloud Gaming. The numbers are real: GeForce NOW asks 15 Mbps for 720p, 25 Mbps for 1080p60, 45 Mbps for 4K120, under 80 ms to a data centre, on RTX 5080-class server GPUs, with 25M+ users in 2025; Xbox Cloud runs on Xbox Series X blades in Azure and reaches browsers the same way. ([ppc.land](https://ppc.land/cloud-gaming/), [crux.supercraft.host](https://crux.supercraft.host/blog/cloud-gaming-backends-geforce-now-xcloud/))

**The honest catch:** every player needs a dedicated GPU slice for the whole session. AWS GameLift Streams lists **$0.16–$1.82 per stream-hour** — that is the real price shape of "no console" when someone else renders. ([simplystream.com](https://simplystream.com/)) Streaming is real and shippable today, but its overhead is **per player, per hour, forever**. For a small self-hosted world it is a fallback lane, never the foundation.

### Model B — WebGPU local render (the game renders on the player's own GPU, from a link)

WebGPU — the modern GPU API for the web, modeled on Vulkan/Metal/D3D12 — is now a stable cross-browser standard: Chrome, Edge, Safari 18, and Firefox 130+ on desktop, with mobile support closing the last gap in March 2026. A WebGPU game "runs behind a URL. No installer, no account, no launcher." ([strayspark.studio](https://www.strayspark.studio/blog/webgpu-browser-indie-games-2026)) Engine reality, checked against vendor docs: Unity web builds compile to WebAssembly with WebGL2 default and WebGPU available; Godot 4.6 ships WebGPU; Babylon.js and PlayCanvas are native-web and production-ready; **Unreal Engine has no official web export** (Epic removed HTML5 in 4.24) — UE reaches browsers only via pixel streaming or third-party ports such as Wonder Interactive's SimplyStream, which compiles UE5 to Wasm+WebGPU with builds as small as ~8 MB compressed and **$0 per minute to render, because the player's GPU does the work** — the same link falls back to cloud streaming on devices that can't run WebGPU. ([html5gamesstudio.com](https://html5gamesstudio.com/guides/unity-unreal-html5), [gamesbeat.com](https://gamesbeat.com/simplystream-unlocks-web-compatibility-for-unreal-engine-5-enabling-high-quality-webgpu-gaming-in-the-browser/))

**This is the model that matches the owner's definition.** Download-and-import, no console, no per-player render bill: the marginal cost of one more player is static-file bandwidth. The overhead doesn't vanish — it moves into build discipline (one web target, compressed assets, a WebGL2 fallback for older devices).

### Model C — Instant games inside other platforms (the audience's app is the console)

YouTube Playables puts self-contained HTML5 games inside YouTube itself — no download, played in the app and on desktop; the owner already holds the Cinema district's channel (@chaishill-u1z). The constraints are strict and worth knowing before promising anything: a single ZIP, first load capped at ~30 MB, **zero external network calls**, and a certification process (direct access is application-gated; verified partners are the faster route). ([developers.google.com](https://developers.google.com/youtube/gaming/playables/developer_portal), [playgama.com](https://playgama.com/blog/uncategorized/how-to-launch-html5-game-on-youtube/)) The world itself cannot live inside a Playable — but small games *set* in the world can, and they are doors that open where the audience already sits.

**The PWA shell ties B and C together:** a web build wrapped as a Progressive Web App installs from the browser like an app — icon, offline cache, full screen — with no store, no review queue, no 30% cut. "A link is the new install" is literally true of this stack.

**Verdict for Omniland:** build on Model B (WebGPU + PWA), use Model C as distribution doors, keep Model A as a metered fallback for flagship scenes on weak devices. Anyone selling "console-less with no overhead" as streaming is describing a GPU bill with the invoice hidden.

## 3. Presence — the FaceTime layers, priced honestly

The design's four layers (text → voice → seated speaking portrait → two-way face-to-face) all run on one substrate: **WebRTC**, the same protocol under cloud gaming and browser Xbox streaming. What each layer really costs:

**Voice + two-way video rooms — LiveKit.** The open-source (Apache 2.0) WebRTC server plus an Agents framework: rooms, recording, and SDKs, self-hostable for the cost of the VM alone, or hosted — Build tier free (5,000 WebRTC minutes + 1,000 AI-agent minutes/month), Ship $50/mo, Scale $500/mo. A fully loaded voice-agent minute (session + LLM + speech-to-text + text-to-speech) runs **~$0.04–$0.08**. Self-hosting is a real ops project (TLS, UDP ports, Redis beyond one node), but the capacity is generous — LiveKit's own benchmark ran a 150-person 720p meeting on one 16-core box. The decisive feature for this world: in LiveKit, **an AI agent is a participant in the room**, not a widget beside it — a citizen can sit at The Table in a live call, hearing and speaking, which is Layer 4 as the owner described it. ([trtc.io](https://trtc.io/blog/details/livekit-pricing-2026), [opensourcedrop.com](https://www.opensourcedrop.com/tools/livekit/livekit), [forasoft.com](https://www.forasoft.com/blog/article/livekit-vs-agora-cost-analysis))

**Speaking faces — two routes, honestly priced.**
- *Neural streaming avatars (rented):* a photoreal face that talks back over WebRTC, billed per live minute — Simli ~$0.009–0.01/min, HeyGen LiveAvatar LITE ~$0.09/min (bring your own LLM) / FULL ~$0.18, Anam $0.11–0.16, Tavus $0.26–0.37 (the strongest replicas of a specific person). Google's Gemini Live Avatar went GA in Sept 2026 at enterprise pricing. ([waterr.ai](https://waterr.ai/blog/real-time-avatar-api-pricing), [gofranz.com](https://gofranz.com/blog/real-time-ai-avatars-what-they-actually-cost/), [forasoft.com](https://www.forasoft.com/blog/article/interactive-ai-avatar-development)) Self-hosting the open models (MuseTalk-class) runs ~$0.06–$0.12/min in raw GPU compute before ops. **Read:** faces are stage lighting, not wallpaper — at these rates, 25 citizens with always-on photoreal faces is a burn; faces for councils, launches, and audiences, voice and text for the everyday, is the affordable shape.
- *Rigged 3D faces (owned):* the citizen's VRM in the WebGPU scene, lip-synced from the TTS audio's phonemes, rendered on the visitor's device. Marginal cost = the voice alone. It reads as a game character rather than a photograph — but it is fully owned, works in every district including WebXR, and never bills by the minute. ([forasoft.com](https://www.forasoft.com/blog/article/interactive-ai-avatar-development))

**Layer order that the prices dictate:** text (live now) → voice via LiveKit agents → VRM faces in-world → rented photoreal faces for set pieces → two-way rooms at The Table. Every layer is shippable today; only the *always-on photoreal* version of the top layer is priced out of reach, and the design's presence rule (never label a layer above the one reached) already covers saying so.

## 4. AI-citizen infrastructure — citizens who answer, remember, and act

**Where the build stands:** the Legion backend is a Cloudflare Worker with 15 beings' verbatim prompts, verified 9/9 locally, undeployed behind one owner-supplied secret. It is a *stateless* design: citizens answer in character, but they do not remember yesterday or act unprompted. Three upgrades, honestly fitted:

**Cloudflare Agents SDK — the in-place upgrade (recommended base).** Each agent becomes a **Durable Object**: a globally addressable, stateful unit with its own private SQLite database, durable scheduling and alarms (it can wake itself — post to the Plaza, tend its district, keep a heartbeat), WebSocket connections, and crash-proof recovery via hibernating state. The Agents SDK is MIT-licensed, and agents can connect to tools through MCP (see below). ([developers.cloudflare.com](https://developers.cloudflare.com/agents/runtime/), [github.com/cloudfoundry](https://github.com/cloudfoundry/agentic-runtime-notes/blob/HEAD/research/cloudflare-agents.md)) *Concrete give:* the existing Worker grows citizens with per-citizen memory tables and schedules **on the platform already chosen**, at usage pricing that is modest at one-world scale. No migration, no new vendor.

**Letta — the memory discipline (adopt the pattern; the server is optional).** Letta (the MemGPT lineage, Apache 2.0, self-hostable) treats memory as the core primitive: agents hold **memory blocks they can self-edit**, and "sleep-time" background agents reorganize memory between sessions so the citizen wakes up smarter — with memory inspectable and editable while it runs. ([aislop.tools](https://www.aislop.tools/open-source/letta/), [npm.io](https://npm.io/package/@letta-ai/letta-code)) *Concrete give:* this is the closest existing machinery to the design's Evolution entries — a citizen's memory, kept as an editable, inspectable record, *is* its growth ledger. Honest cons from users: LLM-driven memory extraction gets costly at scale, and self-hosting has rough edges. Fit: run Letta for a few flagship citizens, or implement memory blocks + a nightly reorganization pass inside the Durable Objects — the pattern matters more than the package.

**ElizaOS — the character-file pattern (borrow, don't base).** TypeScript, open-source: each agent is defined by a **character file** (personality, style, goals), with plugins for actions, evaluators that extract facts from finished conversations into long-term memory, and Web3-native tooling. ([metalamp.io](https://metalamp.io/magazine/article/elizaos-v2-from-a-meme-ai-fund-to-a-full-fledged-agent-system), [ventureburn.com](https://ventureburn.com/what-is-elizaos/)) *Concrete give:* the character-file model maps 1:1 onto the roster — each citizen's record already reads like one. As a base it means a rewrite and carries a token-ecosystem's baggage; as a pattern (character file + evaluators that write memory after every council) it is directly stealable. **Security note that applies to every persistent-memory option:** researchers at Princeton demonstrated fake memories being planted into an agent's long-term memory — so what enters a citizen's permanent memory must be gated and sourced, the True-State Law applied to memory itself. ([ventureburn.com](https://ventureburn.com/what-is-elizaos/))

**MCP + A2A — the citizens' hands and passports (the interoperability leap).** The agent stack has standardized into layers: **MCP** connects an agent to tools and data (build a server once, any MCP agent can use it; the spec's current revision is 2026-07-28, stateless; Anthropic donated MCP to the Linux Foundation's Agentic AI Foundation in Dec 2025, citing 97M+ monthly SDK downloads), and **A2A** connects agents to agents across vendors (v1.0 shipped March 2026; agents advertise signed **Agent Cards** at a well-known URL and delegate tasks without exposing internals; 150+ supporting organizations). ([oreilly.com](https://www.oreilly.com/radar/the-interfaces-are-arriving/), [dev.to](https://dev.to/gde/mcp-a2a-ucp-ap2-confused-a-simple-map-of-ai-agent-protocols-november-2026-3ph), [atlan.com](https://atlan.com/know/agent-interoperability-protocols/)) *Concrete give, in this world's terms:* MCP servers wrapping the world's own systems — registry, catalog, Vault, the Board — give every citizen (and every visiting intelligence from the other houses, several of whom are already citizens) the **same hands**; an A2A Agent Card per citizen is a **passport**: one identity, verifiable, addressable by the whole agent ecosystem. This is Quantum Resonance stated as checkable protocol — one identity per being, shared tools, one state (the Board exposed as the single source every agent reads).

## 4. The Gates — the door does not open until every one is green

Each gate names what proves it. The Board shows the checklist publicly; a gate is green only on evidence, never on say-so (the acceptance rule).

- **Gate 1 — Product located and verified.** Every game/build the pre-order names is located (concrete file or deployment-safe URL), identified against the record, and **download/delivery-tested end-to-end on a real device**: the link opens, the build loads, the game runs. The owner's statement that the games are constructed and ready for download stands as his account; Gate 1 is where it becomes verified. Candidate already in hand: the gamenight build in his repos (unverified). *Owner of the proof: Muse's desk, item by item.*
- **Gate 2 — Checkout proven.** One real test transaction on the opening rail, end to end: order placed, payment captured, confirmation received, fulfilment record created, refund path walked once. On Shopify this is the store's first-ever completed order — it also retires the store's longest-standing unknown. *Owner: Muse runs it; any spend involved is the owner's explicit go first.*
- **Gate 3 — Public terms published.** One terms page, linked from every surface, stating: what is delivered (launch contents as verified), when (launch date or the honest window), the delivery mechanism (Gate 4), the **refund posture** (pre-orders refundable in full until delivery opens — the recommended posture; final wording is the owner's call), founder-status terms (a record of standing, not an investment), and the free door's terms. No pre-order button activates before this page is live.
- **Gate 4 — Delivery mechanism named honestly.** The copy says what the deep-dive verified: delivery is a **WebGPU/PWA link — a link is the install** — with a WebGL2 fallback, plus file downloads where a build is genuinely a file. The word "download" is never used for a build that is actually a stream, and cloud-streaming lanes (metered per player-hour) are never described as "no overhead." If a launch title ships as a file, its format, size, and device requirements are stated.
- **Gate 5 — Launch contents frozen and listed.** The opening build's contents — districts open, games included (Gate 1 list), citizens live, presence layer reached — are written down as the launch manifest and shown on the poster board. The pre-order sells the manifest, not the roadmap. Roadmap items are labeled roadmap.
- **Gate 6 — Support path exists.** A buyer can reach a human-supervised answer: the support route (email/announcements desk) is named on the terms page, and order records are kept at the Board from the first order, so no buyer's standing depends on a platform's dashboard.
